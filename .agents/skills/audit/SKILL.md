# Audit Work Block

1. Leer completos `AGENTS.md`, `docs/development_protocol.md` y `.agents/rules/investment-analyst-core.md` en una sesión fresca e independiente por Work Block. Resolver fail-closed el único Work Block y su target desde estado vivo; releer literalmente Issue, expected branch, base y SHA. Antes de exigir un PR abierto, distinguir el flujo normal de la continuación postmerge pendiente descrita en «Recuperación postmerge de entrega local»: Issue cerrado o ausencia de label no acreditan despliegue; sólo la identidad y autorización demostradas del PR fusionado la habilitan, sin elegir «el último» ni degradar un runtime más nuevo. Resolver instrucciones, protocolo y guard desde la base integrada verificada, no desde un primary atrasado ni rutas candidatas; si el primary está atrasado, registrar la ruta y el digest del ejecutable usado y comprobar que coincide con el authority snapshot, sin confundir un snapshot correcto con el script correcto. Para `BUILD_GOVERNANCE`, materializar y verificar el authority snapshot de base: los bytes candidatos son input no confiable hasta merge. Ejecutar `scripts/check_workflow_guards.py --live --phase audit` antes y después de reconciliar el marker; `--json` es diagnóstico no autoritativo y no puede resolver el target ni un gate. Modelo/cliente es metadata, no autoridad.
2. AUDIT es read-only respecto de source, branch, head, estado del candidato y workspace permanente: no ejecuta formatter, fixer ni comandos mutantes como `gh pr ready`, merge, cleanup, cierre del Issue o cambios de label. La única mutación autorizada es la estrecha y machine-owned del propio comentario AUDIT para publicar o reconciliar evidencia exact-SHA; no puede alterar source, branch, head ni estado irreversible. La entrega local del merge también pertenece sólo al FINALIZE autorizado. Antes de PASS intenta refutar el candidato. Contabilizar todos los archivos del diff base...SHA, inspeccionar el diff completo y contexto crítico, justificar exclusiones no materiales y mapear independientemente cada ID del manifest (acceptance, invariante y negativo) a evidencia observable. BUILD/CI/smoke o filenames nunca sustituyen esta revisión semántica.
3. Reutilizar el gate literal `Python 3.12 quality` verde y ejecutar a lo sumo una prueba focalizada read-only por riesgo concreto. Verificar SHA vivo, BUILD único PASS, smoke, requested changes, threads y probes de cada fallo material BUILD/FIX, o declarar que no existieron. Reconciliar todos los markers AUDIT según el algoritmo global antes de publicar/actualizar el único PASS/FAIL con rango, contabilidad, matriz de evidencia, hallazgos y riesgo.
4. BLOCKER, MAJOR, evidencia crítica ausente, diff material incompleto, identificador stale/sintetizado, contradicción sin resolver, test debilitado sin equivalencia o probe sin verificar impiden PASS. Cuando la evaluación llega legítimamente a un resultado terminal, AUDIT siempre publica o reconcilia primero su único marker machine-owned exact-SHA con manifest SHA-256 y verdict por ID: un resultado FAIL registra `status=FAIL` y termina `CHANGES REQUIRED`; un resultado PASS registra `status=PASS`. Después de esa mutación estrecha relee GitHub y ejecuta nuevamente `scripts/check_workflow_guards.py --phase audit`; no puede devolver PASS sólo en narrativa. Con PASS y policy HUMAN, el handoff termina `AWAITING HUMAN APPROVAL` y ejecuta cero ready/merge/cleanup, cierre del Issue o cambios de label; sólo una instrucción HUMAN puede producir `development-workflow:human-v1` exact-SHA, sin self-review. Sólo con PASS y policy AUTO efectiva, incluida CRITICAL o `BUILD_GOVERNANCE` con standing verificado o legacy de base, termina AUDIT e inicia FINALIZE con un guard `--live --phase finalize` completo pre-ready, `gh pr ready`, y otro guard live completo post-ready antes de confirmar head y hacer squash con `--match-head-commit`; ambos releen el mismo grant en main vivo y una revocación o cambio detiene. Tras el merge, la misma transición ejecuta la entrega local del protocolo sobre `mergeCommit.oid` antes del cleanup; `--skip-systemd` y `--skip-health-check` están prohibidos en un servicio gestionado y un fallo es `FINALIZATION BLOCKED`. Una entrega fallida postmerge se reconoce como continuación, nunca como bootstrap ni nuevo PR. Nunca usa admin/bypass y reconcilia Issue/label idempotentemente. Un GUARD FAILURE previo a un resultado legítimo conserva el fail-closed del guard y no muta evidencia ajena.

## Entrega local postmerge

5. Sólo dentro del FINALIZE autorizado, tras AUDIT PASS y merge, obtener `mergeCommit.oid`; desde el checkout verificado ejecutar `scripts/deploy_local_release.py update --sha <mergeSHA>` y `status --json`, y verificar SHA exacto, unidad/proceso cargados, `NeedDaemonReload=no`, HTTP 200 y mismo workspace/binding. Ejecutar el smoke del bloque y sólo las operaciones postmerge expresamente autorizadas por su scope; no reproducir el parser ni la receta del protocolo.

6. Antes del cleanup publicar un recibo compacto: PR/head/mergeSHA, runtimeSHA, unidad/proceso/`NeedDaemonReload`, HTTP/workspace, smoke y aceptación postmerge, límites y enlace de evidencia. Es un comentario normal, no un marker ni schema nuevo. Un HTTP 200 del release anterior, un estado de disco sin proceso actualizado, un readiness premerge o un merge exitoso no son entrega: sin verificación exacta es `FINALIZATION BLOCKED`, con el pendiente visible y sin cleanup, cierre ni retirada de label. `--skip-systemd` y `--skip-health-check` están prohibidos.

La entrega local forma parte del FINALIZE AUTO y no requiere una autorización narrativa adicional del Issue; las adquisiciones o escrituras de dominio adicionales sí exigen scope explícito del bloque. AUDIT no despliega ni recibe permiso general para escribir el workspace: permanece read-only y FINALIZE es una transición separada. No se altera el scope ni las superficies protegidas del bloque resuelto.

Devolver únicamente `AUDIT PASS`/`CHANGES REQUIRED` o `COMPLETE`/`FINALIZATION BLOCKED`, SHA, hallazgos materiales, riesgo y siguiente acción.
