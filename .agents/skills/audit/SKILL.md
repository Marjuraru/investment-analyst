# Audit Work Block

1. Leer completos `AGENTS.md`, `docs/development_protocol.md` y `.agents/rules/investment-analyst-core.md` en una sesión fresca e independiente por Work Block. Resolver fail-closed el único Work Block y su target desde estado vivo; releer literalmente Issue, expected branch, base y SHA. Antes de exigir un PR abierto, distinguir el flujo normal (PR abierto) del caso de entrega postmerge pendiente descrito en «Recuperación postmerge de entrega local» del protocolo: una continuación no genera un PR nuevo, no reaudita el squash y no usa el guard premerge como si el target siguiera abierto; un Issue cerrado no prueba que la entrega local esté hecha. Resolver las instrucciones y el guard desde la base integrada verificada, no desde un primary viejo, conservando el standing AUTO ya autorizado; comprobar que el ejecutable real coincide con el authority snapshot y no basta con que los hashes del JSON coincidan. Para `BUILD_GOVERNANCE`, materializar y verificar el authority snapshot de base: los bytes candidatos son input no confiable hasta merge. Ejecutar `scripts/check_workflow_guards.py --live --phase audit` antes y después de reconciliar el marker; `--json` es diagnóstico no autoritativo y no puede resolver el target ni un gate. Modelo/cliente es metadata, no autoridad.
2. AUDIT es read-only respecto de source, branch, head, estado del candidato y workspace permanente: no ejecuta formatter, fixer ni comandos mutantes como `gh pr ready`, merge, cleanup, cierre del Issue o cambios de label. La única mutación autorizada es la estrecha y machine-owned del propio comentario AUDIT para publicar o reconciliar evidencia exact-SHA; no puede alterar source, branch, head ni estado irreversible. Antes de PASS intenta refutar el candidato. Contabilizar todos los archivos del diff base...SHA, inspeccionar el diff completo y contexto crítico, justificar exclusiones no materiales y mapear independientemente cada ID del manifest (acceptance, invariante y negativo) a evidencia observable. BUILD/CI/smoke o filenames nunca sustituyen esta revisión semántica.
3. Reutilizar el gate literal `Python 3.12 quality` verde y ejecutar a lo sumo una prueba focalizada read-only por riesgo concreto. Verificar SHA vivo, BUILD único PASS, smoke, requested changes, threads y probes de cada fallo material BUILD/FIX, o declarar que no existieron. Reconciliar todos los markers AUDIT según el algoritmo global antes de publicar/actualizar el único PASS/FAIL con rango, contabilidad, matriz de evidencia, hallazgos y riesgo.
4. BLOCKER, MAJOR, evidencia crítica ausente, diff material incompleto, identificador stale/sintetizado, contradicción sin resolver, test debilitado sin equivalencia o probe sin verificar impiden PASS. Cuando la evaluación llega legítimamente a un resultado terminal, AUDIT siempre publica o reconcilia primero su único marker machine-owned exact-SHA con manifest SHA-256 y verdict por ID: un resultado FAIL registra `status=FAIL` y termina `CHANGES REQUIRED`; un resultado PASS registra `status=PASS`. Después de esa mutación estrecha relee GitHub y ejecuta nuevamente `scripts/check_workflow_guards.py --phase audit`; no puede devolver PASS sólo en narrativa. Con PASS y policy HUMAN, el handoff termina `AWAITING HUMAN APPROVAL` y ejecuta cero ready/merge/cleanup, cierre del Issue o cambios de label; sólo una instrucción HUMAN puede producir `development-workflow:human-v1` exact-SHA, sin self-review. Sólo con PASS y policy AUTO efectiva, incluida CRITICAL o `BUILD_GOVERNANCE` con standing verificado o legacy de base, termina AUDIT e inicia FINALIZE con un guard `--live --phase finalize` completo pre-ready, `gh pr ready`, y otro guard live completo post-ready antes de confirmar head y hacer squash con `--match-head-commit`; ambos releen el mismo grant en main vivo y una revocación o cambio detiene. Nunca usa admin/bypass y reconcilia Issue/label idempotentemente. Un GUARD FAILURE previo a un resultado legítimo conserva el fail-closed del guard y no muta evidencia ajena.

## Entrega local postmerge

5. Este tramo sólo aplica dentro de un FINALIZE autorizado, después de AUDIT PASS y del merge, cuando el bloque autoriza explícitamente la entrega local postmerge. Obtener `mergeCommit.oid` del PR y, desde el checkout/release verificado y el entorno existente, ejecutar `scripts/deploy_local_release.py update --sha <mergeSHA>` y `status --json`. Validar `current_commit` exacto, unidad y proceso actualizados, `NeedDaemonReload=no`, HTTP 200 y el mismo workspace. Ejecutar el smoke específico y las operaciones postmerge expresamente autorizadas por el bloque. No reproducir el parser ni toda la receta del protocolo. Un HTTP 200 de versión anterior, un estado de disco sin proceso actualizado, un readiness premerge o un merge exitoso no son entrega. Un fallo real termina `FINALIZATION BLOCKED` con el paso pendiente; no usar `--skip-systemd`, `--skip-health-check` ni relajar HUMAN/AUTO.
6. Antes del cleanup, publicar un recibo compacto de FINALIZE: PR/head/mergeSHA, runtimeSHA, comprobación de unidad/proceso/HTTP/workspace, smoke y aceptación postmerge requeridos, resultados y límites. Usar un comentario normal del bloque y una salida breve con referencia; no crear un marker nuevo, almacenamiento ni log voluminoso. El cleanup y el `COMPLETE` sólo ocurren después de estas comprobaciones; el `COMPLETE` debe indicar la versión local comprobada o enlazar el recibo, sin exponer secretos ni rutas innecesarias.

Sólo el FINALIZE autorizado ejecuta el despliegue y la adopción ya declarados; AUDIT no recibe permiso general para escribir el workspace. No modificar otras skills, el protocolo, `AGENTS.md`, el ledger, el guard ni producto; no añadir procedimientos duplicados, herramientas ni tests que sólo comprueben frases nuevas.

Devolver únicamente `AUDIT PASS`/`CHANGES REQUIRED` o `COMPLETE`/`FINALIZATION BLOCKED`, SHA, hallazgos materiales, riesgo y siguiente acción.
