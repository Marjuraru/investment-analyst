# Build Work Block

1. Leer completos `AGENTS.md`, `docs/development_protocol.md` y el Issue resuelto. Resolver el Work Block activo, base, expected branch y PR exclusivamente desde estado vivo; descartar referencias de bloques anteriores conservadas en hilo o cliente y nunca usar el último Issue, PR o rama como target. Antes de la primera mutación de archivo, verificar que el worktree activo es aislado para la expected branch, la rama actual es la esperada, el SHA base declarado está adquirido y verificado, y el checkout primario de la base permanece limpio y no es destino de escritura. Ante escritura fuera del worktree autorizado, detenerse sin stash, reset, clean, checkout ni switch forzado, devolver `BUILD GUARD FAILURE` con la contradicción y rutas afectadas, y dejar su reubicación o descarte a decisión humana explícita. Ejecutar preflight Git y resolver fail-closed el único Issue activo, base, expected branch, writer role, profile, policy, scope y gates; modelo/cliente nunca altera permisos.
2. Resolver el PR sólo por expected branch. En BUILD, cero PR es `BUILD BOOTSTRAP` no terminal; crear el primer commit real y draft PR. Adquirir una base remota ausente y crear una rama ausente únicamente desde su SHA remoto verificado, sin stash/reset/clean/force/overwrite. Si existe, exigir branch/worktree compatibles. Ejecutar `scripts/check_workflow_guards.py --live --phase build`: sólo su adquisición autoritativa materializa rutas, policy, scope y hashes; `--json` no puede resolver ni gatear. Contradicciones son `BUILD GUARD FAILURE` sin reparar archivos.
3. Antes de implementación material, ejecutar el capability preflight: derivar las necesidades declaradas y previsibles, comprobar CLI/configuración sin secretos, permisos GitHub y accesos. Agrupar al inicio como máximo una solicitud externa previsible y acotada.
4. Ser el único writer. Para R3/superficie sensible, tocar exclusivamente la strict allowlist; en otro caso respetar semantic scope, superficies protegidas y prohibidas. Implementar el mínimo cohesivo y corregir sólo hallazgos del mismo PR.
5. Aplicar tras cada acción la tabla canónica del protocolo: CONTINUE ejecuta, FIX corrige, WAIT/POLL espera hasta terminal. BUILD puede ejecutar formatter/fixer dentro de scope y vuelve a validar su resultado. Un `BUILD BLOCKED` nombra la fila concreta de la tabla y el recurso o autoridad exacta ausente; duración, cantidad de pasos y trabajo restante nunca bloquean, y CI, smoke, validación interna o cierre previos a PR/AUDIT pendientes resuelven WAIT/POLL o CONTINUE. READY exige markers canónicos, guard común PASS, gate literal `Python 3.12 quality`, estados terminales reconocidos y ninguna acción obligatoria pendiente. Los perfiles FAST/AUTO sólo pueden llegar a FINALIZE con dos guards `--live --phase finalize` completos e independientes, separados por `gh pr ready`. Ejecutar Ruff, pruebas focalizadas y smoke real requerido; usar `scripts/check.sh` sólo bajo sus excepciones. Revisar diff completo, secretos, compatibilidad, scope y trabajo protegido.
6. Stagear sólo el alcance previsto, commit, push y fijar el SHA completo. Crear o actualizar un único PR draft contra la base declarada con body estable. Reconciliar primero todos los markers BUILD; `PENDING` sólo cubre recuperación owner-only o espera real y nunca es un handoff rutinario. Publicar/actualizar `PASS` únicamente cuando todos los gates del SHA exacto estén completos, con acceptance, negativos, hashes, referencias y riesgos.
7. Esperar `Python 3.12 quality` terminal para ese SHA, ejecutar el smoke de descubribilidad/comportamiento y reconciliar target, head y evidencia. Antes de responder, ejecutar el pre-return terminality check; si queda una acción autorizada, continuar. Sólo FAST/AUTO puede pasar a los dos snapshots de FINALIZE; cualquier otro perfil permanece draft.

Mientras haya una acción autorizada cuyo propietario sea BUILD, continuar; bootstrap, commit, PR o CI parcial no son salida. Responder sólo `BUILD READY`, `BUILD BLOCKED` o `BUILD GUARD FAILURE`, PR/SHA, capacidad, gates, riesgo material y siguiente acción. Un commit invalida evidencia previa.
